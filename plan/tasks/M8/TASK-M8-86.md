## Goal
The native app's egui GUI with the mock engine (R-390), compiled to `wasm32-unknown-unknown` and running on WebGPU in the
browser, deployed to the GitHub Pages site, https://ma1achy.github.io/Principia/, by hand only (R-627). It runs in a Web
Worker on an OffscreenCanvas if it will run there; if it will not, it runs in the fallback that does (egui's own web
runner on the main thread). It carries the measurement panel and the scripted pan that TASK-M8-96 measures with, on the
deployed site, against RQ-550 and RQ-551 (split by code review 5663981956 of R-627's port, F1, applied per R-369). It is
a skeleton: no real engine, no frame loop of the engine's, no membrane design; v1 web proper is TASK-M8-37's and
TASK-M8-38's, built on it.

## Deliverables
- The gui crate and the engine contract it uses build for `wasm32-unknown-unknown` with the mock engine and WebGPU
  (`eframe`'s web runner, or egui with egui-wgpu driven directly in the worker); a wasm entry in `crates/gui` behind a
  `web` feature, the native build unchanged. Any dependency added for it is named in the PR with its reason.
- `web/skeleton/`: `index.html`, the vendored `coi-serviceworker.js` beside it (self-hosted, same origin, no CDN;
  caching_contract Part 6a), the worker script that starts the app on the OffscreenCanvas it is sent, and the
  main-thread loader that transfers the canvas once and forwards what the worker cannot receive itself (pointer, keys,
  text, resize), each forward listed in the PR.
- A build command (`cargo xtask web-skeleton`, or the tool the PR names) that writes the site to one directory, the wasm
  bindings generated by `wasm-bindgen` at a pinned version.
- `.github/workflows/pages.yml`: `on: workflow_dispatch` only; one build job and one deploy job, the deploy job running
  only when `github.ref == 'refs/heads/main'`, with `environment: github-pages`, `permissions: pages: write,
  id-token: write`, through `actions/upload-pages-artifact` and `actions/deploy-pages` at pinned versions; no
  `push`, `pull_request`, `schedule` or other trigger (R-627).
- `xtask/tests/pages_workflow.rs` (or a unit test in xtask): `pages_workflow_manual`, reading the workflow file.
- A measurement page or panel in the skeleton that reports `crossOriginIsolated`, whether `SharedArrayBuffer` exists,
  the wasm-threads probe's result (a wasm module on a shared `WebAssembly.Memory`, a second worker writing a value the
  first reads through `Atomics`), the layout the app runs in, and the frame rate over a timed window; and a scripted
  pan for the frame-rate runs. The panel is never drawn over the figure (render_gui_spec G1 holds in v1 web, R-571): it
  is opened by a URL flag, `?measure`, in the browser, and natively by the environment variable `PRIN_MEASURE=1`, the
  same panel in both builds, beside the figure in the view the figure is already in. It is not R-467's View › Debug view,
  which is a figure toggle with a SetField, an undo entry and the hatch (REQ-GUI-225), and opening the panel edits no
  state or history, so both builds measure with the same figure view. It is the skeleton's only: TASK-M8-37
  may keep it or drop it (gui review 5664362471 of R-627's port, G5, applied per R-369).
- The skeleton's wasm build in CI (a build-only job in `ci.yml`), so a later change that breaks it is seen (applied per
  R-369).
- **What TASK-M8-96 measures with**, all here, since TASK-M8-96 changes no code (qa review 5665189777 of R-627's port, F2 and F4, applied per
  R-369):
  - The browser runner: `web/skeleton/runner/package.json` and its `package-lock.json`, pinning `@playwright/test` and
    a WebDriver client; a Chrome script (Playwright on the installed Chrome stable, `channel: "chrome"`) and a Safari
    script (WebDriver through `safaridriver`), each loading a given URL in a given layout, running the scripted pan and
    idle, and writing the panel's fields as JSON. `plan/HUMAN_SETUP.md` §6 and TASK-M8-96 use these scripts.
  - The same scripted pan and frame-rate window in the native mock app (`cargo run -p gui --features mock`), in the
    same measurement panel the web build shows under `?measure`, opened natively by `PRIN_MEASURE=1` (not R-467's View
    › Debug view), reporting the same fields with the same figure view, so REQ-PERF-115 compares native and web on one
    method.
  - A way to force each layout: `?layout=worker` (a Web Worker on an OffscreenCanvas) and `?layout=main` (egui's web
    runner on the main thread); when the worker layout fails, the panel records the reason (the error, or the missing
    API) and the layout it fell back to.
  - The frame statistics, one implementation in `crates/gui` for both builds. The display's refresh rate is measured
    apart from the app's work: in the browser, an empty `requestAnimationFrame` loop on the main thread, run for 2 s
    before the warm-up with the app idle, its median interval (an app frame that overruns slows `requestAnimationFrame`
    to the app's own rate, so the app's intervals cannot give it); natively, the monitor's rate as winit reports it,
    which the app's work does not change. The per-frame work time in ms runs from the frame's start to its submit (mean
    and 95th percentile). The window is the 30 s that follows a 5 s warm-up, during the scripted pan (the view panned at
    a constant rate of one figure width every 5 s, back and forth) or idle (no input). The mean fps is the number of
    frames presented in the window divided by the window's duration. The 5th-percentile fps is the 5th percentile, by
    the nearest-rank method, of `1000 / interval_ms` over every frame presented in the window. Each reported figure, the
    mean fps or the 5th-percentile fps, is marked "capped" when it is within 2% of the measured refresh rate, since it
    then reads the display, not the work. A debug flag (`?frame_delay_ms=N` in the browser, an environment variable
    natively) adds a fixed delay to each frame's work, for the control below. Test `frame_window_stats`.

- `cargo test -p gui frame_window_stats` — on a synthetic sequence of frame timestamps and work times: the mean fps as the frames presented in the 30 s window after the 5 s warm-up divided by the window's duration; the 5th-percentile fps by the nearest rank over those frames' `1000 / interval_ms`; the per-frame work time's mean and 95th percentile; the refresh rate as the median interval of a given idle loop; and the "capped" mark on each reported figure, mean or 5th percentile, within 2% of that refresh rate, each as defined in the Deliverables; controls: a percentile taken over the warm-up too, one taken over work times instead of intervals, an interpolated percentile where the nearest rank differs, a mean taken as the mean of per-frame fps on a sequence whose intervals are not uniform, so the two differ, a capped mark at 10% on a figure between 2% and 10% below the refresh rate, and a refresh rate taken from the app's own intervals each fail (this task's deliverable "the frame statistics"; qa review 5665189777 of R-627's port, F4).
- Review checklist (gui reviewer), on a local build and on `cargo run -p gui --features mock` — the measurement panel, under `?measure` in the browser and under `PRIN_MEASURE=1` natively, shows in each build the refresh rate, the work time in ms, the mean and 5th-percentile fps and the "capped" mark; `?layout=worker` and `?layout=main` each give that layout, or, for the worker, the recorded reason and the fallback; `web/skeleton/runner/package.json` and `package-lock.json` exist with the pinned versions, and the Chrome and Safari scripts run against the local build on the human's Mac once `plan/HUMAN_SETUP.md` §6 is done, each writing the panel's fields; control: a missing field, a layout flag that is ignored, a script that writes nothing, or a panel that opens only through View › Debug view or adds an undo entry fails the review; and with the per-frame delay flag set so a frame overruns the refresh interval, in the browser and natively, the refresh rate reads the display's true rate and the mean and 5th-percentile fps read uncapped, below it; control: a refresh rate that falls with the delay fails (this task's deliverable "What TASK-M8-96 measures with"; qa review 5665189777 of R-627's port, F2).
